### Новый build-only и регистрация

- Каждый publish направляется в уникальный `artifacts/screen-translate-builds/.staging/<GUID>`. После подготовки manifest/assets и проверки комплектности результат переносится в **новый** `artifacts/screen-translate-builds/<manifest-version>-<GUID>/`; скрипт сообщает точный путь.
- Предыдущие layouts не перезаписываются/не очищаются; ошибка build удаляет только staging текущей попытки. Повторный build той же версии создаёт другую папку. Manifest-version не повышается автоматически.
- `-BuildOnly` допускает работающую старую установку, не требует Developer Mode и не вызывает process/package/registry checks, регистрацию, запуск или остановку процессов. Локальная подготовка файлов/иконок не затрагивает установленный пакет.
- Существующий CLI сохранён: отсутствие `-BuildOnly` означает попытку регистрации после сборки; `-NoLaunch` отключает только launch. Это не команда для текущего безопасного этапа.
- Перед будущей регистрацией проверяются отсутствие процесса, Developer Mode, identity и версия установленного пакета. При relocation manifest-version обязана быть **строго выше установленной**: равная/меньшая версия отклоняется без регистрации. Нужное изменение исходного manifest выполняется пользователем явно, не ради build-only.
- После регистрации проверяются фактические identity/version/InstallLocation до launch. Нет принудительного downgrade/uninstall или обещания транзакционного rollback Windows-регистрации. Зарегистрированный каталог нельзя удалять или перемещать.

### Что покрывают новые изолированные проверки

Script suite использует temp fixtures и подмены всех publish/process/package/DeveloperMode/launch операций. Реальные `Get-AppxPackage`, `Add-AppxPackage`, `Remove-AppxPackage`, dotnet и запуск приложения в этих тестах не вызываются. Проверены BuildOnly при работающем приложении/выключенном Developer Mode/более новой установленной версии; unique same-version builds; сохранность прежних файлов; partial publish failure; неполный runtime/license/assets; испорченная картинка; manifest identity/path traversal; сравнение версий (включая 0.1.0.9 → 0.1.0.10); registration preconditions, неверные InstallLocation/version/publisher и empty/multiple post-registration query results; изменение staged manifest во время publish с отказом до финализации и очисткой staging. Генерация PNG и файловые проверки выполняются реально, но только во временных каталогах.

Добавлены C# regressions FIFO-кэша (132 уникальных записи, сохранение recent, последовательное вытеснение oldest, hit не меняет FIFO) и обоих parser paths (числовые/undefined/pseudo keys, F12, допустимые сочетания и virtual keys). Они вошли в успешный общий Release-прогон **127/127**; старые tests preferred/alternative cache, Bing fallback и cancellation сохранены.

Реализованный контракт UI/координатора, проверенный в пределах автоматизированного набора, а не реальным игровым запуском: полный оригинал либо помещается вместе с переводом, либо идёт отдельными подписанными страницами после перевода; layout измеряется с учётом DPI и доступных ширины/высоты. Ручной desktop selection вне foreground допускается для разового перевода, но repeat-anchor разрешён только для области целиком внутри известных bounds окна и доступного монитора. Изменение контекста/геометрии инвалидирует повтор. Bounds/foreground не выявляют любое перекрытие окна и не обеспечивают полноценный window-content capture.

Startup policy задаёт коды self-test **0** (успех), **1** (ошибка), **2** (экземпляр уже работает, тест не выполнен). В последнем случае activation signal не отправляется и старый `self-test.txt` не меняется; обычный второй запуск активирует настройки. `DiagnosticSink` записывает только структурированные события без PII/распознанного текста/снимков/URL/путей/сообщений исключений: максимум **64 KiB**, запись до 256 байт, очистка прежнего содержимого при превышении лимита. Ожидаемые access/IO/security ошибки не прерывают основной сценарий.
